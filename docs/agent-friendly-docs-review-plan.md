# TinyRobot 文档 Agent 友好化改造

本文从总体执行方案中拆出，作为同事评审时的讲解提纲、演示脚本和验收记录模板。阶段实施状态以[执行方案与进度](agent-friendly-docs-plan.md)为准。

# 同事评审讲解与验收方案

## 评审目的与范围

这次评审要确认：文档 Agent 友好化的整体设计是否解决了开发者和编码助手查找、理解、引用 TinyRobot 文档的问题；静态文档产物、Skill、组件 catalog 与本地 MCP 的职责边界是否清晰；fork 环境的验证证据是否足以支持后续生产化。评审对象是完整设计与当前 fork 验收结果，不是对正式域名、生产凭据或发布自动化的预先批准。

评审范围包括阶段 0–7A 已交付的设计和实现、阶段 5C-Fork 的待验收项，以及评审后生产切换的原则。生产 URL、稳定入口、正式发布凭据、远程 MCP 的主机规格和上线日期都不作为本次前置输入；若评审通过，再把确认后的配置替换到已经验证的方案中。

## 建议的讲解顺序（约 45–60 分钟）

1. **问题与目标（5 分钟）**：说明普通文档页面对 Agent 检索、按需读取和引用的不足；目标是让人和 Agent 使用同一套可验证的文档事实源，而不是另写一套容易过期的答案库。
2. **设计原则与范围（5 分钟）**：展示渐进交付、单一事实源、静态能力可独立使用、环境配置后置四项原则；说明本次不包含业务组件 API 改造、完整 Props/Events/Slots 自动抽取、正式站点切换和远程 MCP 上线。
3. **整体数据流（10 分钟）**：从页面 frontmatter、Markdown、Demo 和公开组件导出出发，经统一 catalog/校验生成 raw Markdown、LLMs 文本、页面/Demo/组件索引和 manifest；静态产物部署到 fork Beta；Skill 按选定站点 manifest 和索引读取文档；本地 MCP 从已生成快照提供搜索、目录发现和按需读取。强调生成产物不另建内容事实源，GitHub Pages 只承担静态托管。
4. **阶段成果（10 分钟）**：依次讲阶段 0–3 的内容与 catalog 基础、阶段 4 页面操作、阶段 5A Skill 收敛、阶段 5B Agent 专区、阶段 6A 轻量组件 catalog、阶段 7A 本地 MCP。每项说明用户可见变化、关键文件/产物和验收状态；明确内置工具组件按约定排除，ChatGPT/Claude 入口按用户决策延期。
5. **Fork Beta 演示（15–20 分钟）**：按下方演示脚本展示网页、静态产物、Skill 和 MCP；每一步均指出它验证了哪条设计约束，并区分已实测证据与待现场补验项目。
6. **风险、待决项和评审结论（10 分钟）**：讨论组件 API catalog 的适用范围、Skill 支持客户端的表述、MCP 搜索质量、远程托管需求/维护责任和 fork 验收门槛；逐项记录结论、责任人和后续验证方式。

## 演示前准备

- 使用维护者 fork Beta 的实际部署 URL，不引用正式站点作为已验收证据；记录本次 Beta 部署的提交、部署时间和 base URL。
- 用与该 Beta 部署提交一致的代码在本地生成 Agent 产物，并确认 manifest 中 `docsVersion=beta`、`publicBaseUrl` 指向 Beta、`sourceCommit` 标记实际提交；对关键 raw/Demo 文件核对 manifest hash。不要复用来源不清晰的临时快照作为评审证明。
- 按 [MCP Server 文档](src/agents/mcp-server.md) 配置独立的 Codex stdio 服务，`DOCS_MCP_CATALOG_DIR` 指向上述本地快照。重启 Codex，现场确认服务已连接且工具清单可见；当前尚无本机 Codex GUI 实连的验证记录，因此这一步是正式演示前的待完成项。
- 准备一个新建或干净的测试对话与可复现问题，不提供项目私有代码或凭据；提前检查浏览器直接访问、刷新和 Beta 子路径下的 raw/index 链接。
- 准备证据目录：部署 URL/提交记录、manifest 摘要与 hash 对照、命令输出、MCP 查询结果、已知限制和演示截图/录屏（如评审团队需要）。记录中不要放令牌、Cookie 或个人配置文件。

## 建议的现场演示脚本

1. 打开 Beta 文档的 Agent 专区，依次进入 LLMs.txt、Skills、MCP Server 页面；刷新子路由并打开 LLMs 两个文件，确认资源能在 Beta base 下访问。
2. 打开一个 Bubble 文档页面，演示复制 Markdown/查看 Markdown 操作，确认演示 tab 下不出现这些页面操作，并说明页面链接与 raw 链接的用途区别。
3. 展示 Beta manifest、pages/demos/components 索引以及一条 raw Markdown，说明它们由构建生成并由哈希关联；以一个已有 Demo 源文件展示索引引用和子路径链接。
4. 在目标 Skill 客户端中给出具体 TinyRobot 任务，让 Skill 先读取 Beta manifest，再定位页面、raw 与 Demo。成功路径应引用所选 Beta 内容；另用错误或缺失 manifest 的地址演示它停止并报告问题，而不是混用本地旧资料或猜测 API。只在目标客户端实际通过后报告该项为通过。
5. 在 Codex 中调用 MCP `search-documentation` 搜索 `useChatRuntimeFromConversation`，再以“TrChat 复用已有会话”搜索中文场景；展示命中页面、章节、摘要和 Beta raw URL。
6. 用搜索结果中的页面 ID 调用章节读取工具，再读取一个 Demo；说明搜索和内容来自本地 Beta 快照，来源链接指向线上 Beta，断网时本地查询仍可用，但不会自动跟随线上更新。
7. 查看组件目录查询 Bubble 的结果，并浏览页面/组件/Demo/Migration Resources；说明当前组件 catalog 是轻量发现索引，不承诺自动提供完整 Props、Events、Slots、Methods 类型文档。
8. 收尾展示“不提供远程 MCP 地址”的状态：GitHub Pages 交付静态文档；若将来要供多人远程连接，需另建支持 MCP HTTP 请求的运行服务，并确定认证、维护和监控责任。

## 需要同事给出结论的问题

- **方案方向**：单一文档事实源生成静态 Agent 产物，并由 Skill 和 MCP 消费，是否能满足开发者与 Agent 的主要查阅场景？是否存在会导致文档内容重复维护的环节？
- **交付范围**：LLMs.txt、Skills、MCP Server 三个 Agent 子页面，以及页面级 Markdown 操作、轻量组件 catalog 的边界是否合理？内置工具组件排除规则是否清楚？
- **组件元数据深度**：当前 catalog 解决“组件是否存在、对应哪页、有哪些示例”的发现问题。评审认为是否还需要抽取 Props/Events/Slots/Methods？若需要，应由具体消费场景和维护成本决定后续范围。
- **Skill 客户端声明**：现有安装/读取流程在哪些具体客户端已实测？对未验证客户端的说明是否足够保守，是否需要把支持范围限制在少数目标客户端？
- **MCP 搜索体验**：标题/关键词/正文词项与中文近似匹配、API 名检索、命中章节/摘要能否支撑演示和开发日常；是否有明确案例证明需要语义检索或 Prompts？
- **本地与远程 MCP**：本地 stdio 是否足以先交付；若多人远程使用，是否有明确价值、维护负责人和安全要求？在这些条件不明确前，是否同意暂不建设远程服务？
- **验收与发布**：Fork Beta 的人工与自动验收证据是否够充分？哪些项必须通过后才可切换正式 URL；是否同意生产发布自动化最后处理？

每个问题记录“通过 / 需要调整 / 暂缓决策”、理由、具体改动、责任人和复验方式。评审意见不等于自动扩大当前实现范围；先确定目标与验收条件，再回到 fork 验证。

## 评审后的路径

- **通过**：冻结评审认可的功能范围和验收标准；进入 5C-Production，替换正式站点配置、验证正式静态产物和链接，然后再处理生产发布自动化。远程 MCP 仅在需求、负责人及运行条件明确后另行实施。
- **需要调整**：将意见转成可验证的变更项，优先在 fork 上修改；只重跑受影响的静态产物、Skill、MCP 或页面验收，再提交复审。
- **暂缓决策**：保持 fork Beta 和本地 MCP 作为验证环境，明确需要补充的证据、决策人和回看时间；不提前写入正式环境地址或部署承诺。
